Test 1 — 100 Duplicate Requests
Fires 100 concurrent charges sharing the same idempotency key. Asserts balance deducted exactly once and only 1 DB record created.
Account: fresh · Balance: $100.00 · Charge: $10.00 · Expected final: $90.00
Test 2 — 50 Distinct Requests
Fires 50 concurrent charges each with a unique key. Asserts SELECT FOR UPDATE prevents lost updates and all 50 land correctly.
Account: fresh · Balance: $1,000.00 · Charge: $15.50 × 50 · Expected final: $225.00
How it works
Idempotency — Test 1
  1. 100 requests arrive simultaneously with the same UUID key.
  2. One wins the race: inserts a Transaction row (UNIQUE constraint on idempotency_key).
  3. The other 99 either find the row on the pre-check and replay it, or catch the IntegrityError and look up the winner's committed response.
  4. Balance deducted exactly once. DB record count = 1.
Row Locking — Test 2
  1. 50 requests each carry a distinct UUID — all are legitimate charges.
  2. Each acquires SELECT … FOR UPDATE on the account row before reading the balance.
  3. Locks serialize updates: each sees the previous committed balance.
  4. All 50 succeed; final balance = $1,000 − 50 × $15.50 = $225.00.
